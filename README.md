# Матричный калькулятор

Лабораторная работа по дисциплине «Объектно-ориентированное
программирование»: класс `Matrix` на C++, вычислительное ядро собрано в
динамическую библиотеку и используется из Python-приложения с
графическим интерфейсом на Tkinter.

Проект демонстрирует:

-   перегрузку операторов в C++ (`+`, `+=`, `*`, `<<`, `>>`);
-   правило трёх (деструктор, конструктор копии, оператор присваивания);
-   экспорт C++ класса через C-ABI (`extern "C"`, `void*`, `try/catch`);
-   загрузку нативной библиотеки из Python через `ctypes`;
-   обработку ошибок C++ как питонячьих исключений;
-   GUI на Tkinter с поддержкой светлой и тёмной темы.

### Интерфейс

-   Две панели ввода (A и B) + панель результата (C).
-   Кнопки операций в отдельной панели.
-   Создание матрицы заданного размера.
-   Заполнение случайными значениями `[0, 10]`.
-   Загрузка из текстового файла и сохранение в файл.
-   Светлая и тёмная темы (переключение в меню).
-   Строка статуса с результатом последней операции.
-   Обработка ошибок через `messagebox` --- приложение не падает.

### Сознательно не реализовано

Следующие функции не входят в рамки лабораторной и не добавлены:

-   Транспонирование, определитель, обратная матрица, ранг.
-   Возведение в степень.
-   Вычитание и умножение на скаляр (нет соответствующих
    C++-операторов).
-   История операций.
-   Undo / Redo.

**Ключевая идея:** математика целиком в C++ (скомпилирована, быстрая),
Python только дёргает готовые функции и отвечает за UI. Все данные
передаются через `void*` --- непрозрачный указатель на C++ объект.
Указатель живёт в куче, пока Python не вызовет `matrix_destroy`.

### Почему C++-исключения не выходят за границу DLL

C++-исключения нельзя перепускать через C-ABI --- это undefined behavior
(на Windows возможен немедленный краш процесса). Поэтому в
`MatrixWrapper.cpp` **каждая** экспортируемая функция обёрнута в
`try/catch`:

\`\`\`cpp EXPORT void\* matrix_add(void\* a, void\* b) { try { ...
return static_cast\<void*\>(new Matrix((*pa) + (\*pb))); } catch (const
std::exception& e) { g_last_error = e.what(); // текст ошибки --- в
thread_local строку return nullptr; // сигнал ошибки --- nullptr } }
Python видит nullptr и читает g_last_error через matrix_last_error(),
затем бросает RuntimeError --- уже нормальное питонячье исключение.

Диагностика проблем OSError: \[WinError 126\] The specified module could
not be found Причина: DLL собрана с динамической линковкой
libgcc/libstdc++/ libwinpthread, и одна из этих DLL не найдена.

Решение: пересоберите с флагом -static (одним, вместо -static-libgcc
-static-libstdc++). Проверьте зависимости через objdump -p MatrixLib.dll
\| findstr "DLL Name".

OSError: \[WinError 193\] %1 is not a valid Win32 application Причина:
разрядность DLL и Python не совпадают. Скорее всего, Python 64-битный, а
g++ --- 32-битный (i686).

Решение: проверьте python -c "import sys; print(sys.maxsize \> 2\*\*32)"
(должно быть True) и g++ -dumpmachine (должно содержать x86_64).
Используйте x86_64-w64-mingw32-g++, а не i686-w64-mingw32-g++.

AttributeError: function 'matrix_create' not found Причина: символ не
экспортирован. Забыли EXPORT, extern "C", или собрали без -shared.

Решение: objdump -p MatrixLib.dll \| findstr matrix\_ --- если пусто,
проверьте MatrixWrapper.cpp.

NameError: name 'Matrix' is not defined в GUI Причина: забыли from
matrix_lib import Matrix в одном из модулей gui/.

Решение: проверьте импорты в widgets.py и app.py.

ModuleNotFoundError: No module named 'gui' Причина: запускаете main.py
не из папки проекта, или в gui/ нет **init**.py.

Решение: cd в папку проекта перед запуском; создайте пустой
gui/**init**.py.

Приложение падает при нажатии кнопки Причина: не все обработчики
обёрнуты в @safe_call, либо исключение не ValueError/RuntimeError
(например, TypeError из-за бага в коде).

Решение: запустите python main.py из терминала --- traceback будет виден
в консоли. Это баг, а не ожидаемая ошибка --- сообщите, если
воспроизводится.

Матрица считается, но результат не тот Причина: пользователь ввёл данные
в неверном формате, парсер «съел» не то.

Решение: после ввода нажмите «A -\> C» (копирование) --- если C
совпадает с A по содержанию, парсер работает правильно. Если нет ---
пришлите содержимое полей.

Тёмная тема применяется не ко всем виджетам Причина: apply_theme
вызывается до создания виджетов, или появились новые виджеты после
применения темы.

Решение: apply_theme должен вызываться последним в **init** и после
любого динамического создания виджетов. Рекурсивный обход
\_paint_text_widgets покрывает все tk.Text и tk.Entry.

Правило трёх (Rule of Three) Класс Matrix владеет double\* data\_,
поэтому:

есть деструктор \~Matrix() --- освобождает data\_;

есть конструктор копии --- глубокое копирование;

есть operator= --- освобождение старого + глубокое копирование.

Если добавите поле-владелец (например, std::vector), правило трёх
автоматически превращается в правило пяти (добавить move-конструктор и
move-присваивание). Пока не нужно.

Почему operator\<\< и operator\>\> --- friend, а не члены Потому что
левый операнд --- std::ostream / std::istream, а не Matrix:

cpp std::cout \<\< m; // нельзя сделать членом Matrix, левый --- cout is
\>\> m; // нельзя сделать членом Matrix, левый --- istream Friend нужен,
чтобы иметь доступ к data\_ (приватное поле) при сериализации.
